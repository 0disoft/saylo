# Vue package release readiness

The Vue 3 adapter is published at `0.1.2` under `latest` with npm provenance, alongside core, React, Svelte, typegen and Vite. It uses Vue major 3 as a peer and depends on the matching core version. The workspace lockfile carries the same version. The [release record](../releases/0.1.2.md) links CI, registry integrity and provenance evidence.

The public package list in `scripts/release-check.mjs` owns release metadata checks, candidate version promotion and source verification, artifact manifests, publication order and package-scoped OIDC checks. Vue participates in all six-package paths. Candidate verification rejects unexpected Vue metadata edits, including restoring `private` or leaving its old version behind.

Run `npm run verify:pack:vue` for focused local readiness. It builds core and Vue, packs both, installs the actual tarballs into an independent app, checks public metadata and JS/TypeScript consumers, and renders concurrent request-local SSR trees and escaped rich text. The full `verify:pack` and registry consumer paths run the same Vue SSR fixture whenever their artifact set contains Vue. Historical four- and five-package approved manifests retain their original package sets and hashes.

The Vite documentation bundle includes the Vue API guide. The preparation checks cover Vue adapter/rich text tests and consumer types, release metadata and lockfile alignment, candidate source integrity, tarball set/integrity rules, mocked OIDC exchanges, historical approvals, and the independent Vue tarball consumer. All six OIDC exchanges and the release CI passed for `0.1.2`. Vue's provenance names the release workflow and source commit, and its SHA-512 matches the CI tarball. The [0.1.1 record](../releases/0.1.1.md) documents the first Vue publication from npm staging.

The Vue npm Trusted Publisher is configured for repository `0disoft/saylo`, workflow `release.yml`, environment `npm-release`, with publication allowed. Future releases run the workflow against final committed source, preserve the successful artifact manifest as a new approved release and verify that exact registry release, including Vue. Local candidate tarballs never replace historical approved manifests. If the target version already exists with different bytes, select a new shared version through the normal candidate process.
