# Live update benchmark

Measures the latency from editing a catalog message during development to its reflection on the screen. The targets are the actual Vite watcher and the actual browser DOM commit.

Paraglide's separate comparison runner is in [../paraglide/README.md](../paraglide/README.md). It optionally installs benchmark-only dependencies in a separate directory and does not add them to the Saylo product packages. Condition differences and results follow [../../docs/13-paraglide-comparison.md](../../docs/13-paraglide-comparison.md).

## Running

Run from the repository root. Build the workspace first, then the Node harness runs.

```sh
npm run bench:live
```

Uses an installed Chrome or Edge in headless mode and creates a separate temporary user-data profile. No additional npm dependencies are required. If no browser is found, specify an executable with `--browser <executable>`.

| Option | Default | Description |
| --- | --- | --- |
| `--scenario` | `all` | One of `1k-3-locales`, `10k-20-locales`, or `all` |
| `--mode` | `edit` | Edit an existing message (`edit`) or add, select, and delete a new locale (`locale-add`) |
| `--samples` | `50` | Number of measurement samples per scenario |
| `--warmup` | `5` | Number of warmups discarded from the measurement |
| `--calibrations` | `25` | Number of control round-trip measurements |
| `--browser` | auto-detect | Chrome or Edge executable path |
| `--out` | `benchmarks/results/live-update.json` | Result JSON path |
| `--no-typegen` | off | Run with typegen disabled |
| `--cpu-profile` | off | Enable a CPU profile of the edit loop during the measurement interval with `node:inspector` and add `cpuProfile` to the results |
| `--browser-stages` | off | Benchmark-only Vite transform. edit collects patch, freeze, and snapshot; locale-add collects full decode, Vite freeze, core acceptOutcome validation and freeze, and snapshot for the first selection, and also distinguishes translator and signature |
| `--server-file-stages` | off | Benchmark-only Node module transform that measures path checks, UTF-8 reads, and catalog parsing separately |
| `--reply-stages` | off | locale-add only. Keeps the default prebundle and collects the server full lookup, encoding, and send, plus the browser hot event receive→DOM time. Do not use together with `--browser-stages` |
| `--client-stages` | off | locale-add only. Keeps the normal prebundle and separately measures client receive→first publication→DOM commit, plus the Vite freeze, core acceptance, and snapshot intervals. Requires `--reply-stages` |
| `--timeout-ms` | `30000` | Per-stage wait timeout |

In `edit` mode, the wire receipt accepts both `saylo:catalog` requests and `saylo:catalog-push` pushes without a separate option. The push receipt starts when it enters the hot listener that Vite registered after parsing the JSON.

## Fixtures and measurement

### Locale-add mode

```sh
npm run bench:live -- --mode locale-add --out benchmarks/results/locale-add.json
```

`locale-app.jsx` and `locale-channel.mjs` add a new en-GB directory and bench.json each round, and confirm the select option appearing, automatic setLocale, the first translation, the return to en, and deletion of the file and directory with option removal. The initial size is the same 1k×3 or 10k×20 as edit, with 1 namespace. There must be 0 catalog transfers before selecting the target. Because receipts count both `saylo:catalog` requests and `saylo:catalog-push` pushes, a push before selection is counted as a transfer instead of being folded into the 0 count, and fails the check. After selection, it requires 1 full response without a known baseline. The schema does not change, so the generated type file must not be rewritten again.

This mode supports `--server-file-stages`, `--browser-stages`, `--reply-stages`, and `--client-stages`, and does not accept `--cpu-profile`. `--client-stages` requires `--reply-stages`, and neither option can be combined with `--browser-stages`. The defaults are warmup 5, 50 measurements, and 25 controls. It separates Node save→list or first-translation ack, and Node selection preparation→translation ack from the browser setter→commit, without mixing clocks. Directory creation and content preparation are excluded from the file save latency. Definitions, results, bytes, and limits follow [../../docs/12-locale-add-measurements.md](../../docs/12-locale-add-measurements.md). The inputs and interval definitions for the default edit mode are below.

```sh
node benchmarks/live-update/run.mjs --mode locale-add --server-file-stages --scenario 10k-20-locales --samples 10 --warmup 2 --calibrations 10 --out benchmarks/results/locale-add-server-files.json
```

Locale-addition instrumentation starts immediately before saving the new file and ends at the list DOM ack. The result's `profiledPhase` is `catalog-addition-before-list-ack`. Each sample stores the existing `serverStages` and the `fileStages` inside it. Initial boot, the full response after selection, the return to en, and deletion are not included in this interval. Therefore `catalogDeltaMs` being 0 does not mean the post-selection load is free; it means it is outside the collection interval. Path checks, reads, and parsing must occur exactly once per round, and multiple file events may be merged in the quiet window. Results and interpretation follow [../../docs/14-locale-add-server-measurements.md](../../docs/14-locale-add-server-measurements.md).
- `1k-3-locales` is 1,000 messages per locale × 3 locales, and `10k-20-locales` is 10,000 per locale × 20. There is 1 namespace.
- The app loads base `ko` and target `en` and renders 1 changed key and 1 unchanged key from `en`'s `bench` namespace. Each save edits only 1 body key in `en`.
- warm means the formatter for unchanged messages is ready. The formatter cost of the modified message is included in the edit cost.
- End-to-end values are measured on a single Node `performance.now` clock, from `writeFile` completion to receiving the HTTP ack body sent after the browser's DOM commit. The time the server broadcasts the manifest and the time the browser receives the catalog and commits it are recorded as separate stages.
- The server stage ends just before the manifest's `ws.send` call. The browser stage runs from when Vite decodes the JSON and it enters the request `saylo:catalog` or push `saylo:catalog-push` hot listener until the DOM check in `useLayoutEffect`. Stringification, transport, and Vite JSON decode costs are included in the end-to-end value but not in the two stage values.
- Ack delivery cost is included in the end-to-end value. Do not add per-stage p95s together, or subtract the server and browser clocks from each other, to construct an end-to-end value.
- The no-op control round trip is also recorded separately and is not subtracted from total latency.
- Statistics use sorted nearest-rank `ceil(n * p) - 1`.
- After an edit that changes only text, confirm that the mtime and size of the generated `.d.ts` are unchanged. typegen is enabled by default and creates the initial `generated.d.ts`.
- Captures the hot event the server passed to `client.send` to timestamp the ack, then computes `wire.catalogReplyBytes` as the UTF-8 size of `JSON.stringify`. This value is the entire event JSON: push includes both manifest and outcomes, and request includes that event's result. Therefore push bytes are not directly comparable to the old single-lookup response. WS headers and compression are not included, and this is not the total physical network bytes. `wire.pushReplies` and `wire.requestReplies` are response counts by transport path, and `wire.patchReplies` and `wire.fullReplies` are response counts by state. `wire.maxChangedMessages` is the patch upsert count (message count for a full response), and `wire.maxPositionUpdates` is `messageCount - upsert` for positionShift, otherwise the positions count.
- When the run ends, delete temporary fixtures and profiles and terminate the browser process and its children together with Vite.

## Server stage instrumentation

`profile.mjs` is a benchmark-only prototype wrapper. Because the library has no clock or profiling API, during the run it temporarily wraps `enqueue`, `startBatch`, `processBatch`, `prepareTranslations`, and `validate` on `LiveRegistry.prototype` and `replace` and `loadDelta` on `CatalogRegistry.prototype` to collect stage times, then restores the original methods. The result's `serverStages` holds these values.

The current result is `boundaryVersion: 3`. v3 starts at the `startBatch` entry of a batch that enters actual serial processing, ends normal batches at `prepareTranslations` entry, and ends superseded or error batches when `processBatch` settles. A drain timer fired while running is not a new batch, so v3 does not use it as a batch start. After a superseded batch, the next `startBatch` may start directly without a drain call, so v3 anchors on `startBatch` entry.

- `queueToDrainMs` is a historical field name kept for continuity. In v3 it runs from the first file event to the first actual `startBatch` entry and includes the quiet window and serialization wait.
- `readAndCandidateMs` is the union of the actual batch intervals in v3. Each batch runs from `startBatch` entry to `prepareTranslations` entry; superseded or error batches run to `processBatch` settle. It includes path validation, file read, parsing, candidate cleanup, and base stat, and is not a separately measured read and parse.
- `translationPreparationMs` is the schema lookup, translation validation, and quarantine preparation time in `LiveRegistry.prepareTranslations`. Normal text edits do not actually quarantine invalid translations, so it is not a measure of quarantine error handling performance.
- `validationMs` is the final `LiveRegistry.validate` of the active catalog after preparation, `registryReplaceMs` is `CatalogRegistry.replace`, and `catalogDeltaMs` is `CatalogRegistry.loadDelta`.
- In results before the quarantine implementation, `readAndCandidateMs` ran to `validate` entry and `translationPreparationMs` did not exist. Translation validation at that time was included in `validationMs`. Do not compare new interval numbers directly with past interval numbers. The save→DOM ack clock and interval definitions are unchanged.
- The v2 boundary was the drain callback. A drain timer fired while running could be mistaken for a batch, and a direct `startBatch` after a superseded batch could be missed. Therefore do not compare `candidateIntervals`, `queueToDrainMs`, or `readAndCandidateMs` from `boundaryVersion` 2 or lower directly with v3 values. Existing result numbers are kept as historical records.
- Do not add stage p95s together or convert them into an end-to-end value.

## Server file stage instrumentation

`--server-file-stages` registers a Node 24 module hook before importing Saylo. `server-file-profile.mjs` wraps the `readCatalogFile` call boundary of the actual typegen `dist/catalog-files.js` only in memory. It does not modify source or dist files, and confirms that the transform was applied. Path check, read, and parse calls must each be observed exactly once per edit, and startup and warmup are excluded from the measurement summary. The hook is removed on exit.

- `pathCheckMs`: realpath-based path confirmation in `assertInside`. It is asynchronous wall time.
- `fileReadMs`: until the actual `read()` (UTF-8 readFile) Promise completes. It mixes disk, OS cache, decoding, and scheduling waits and is not a value for disk I/O or CPU alone.
- `catalogParseMs`: the synchronous `parseCatalog` call and argument construction such as sourceName. It includes JSON processing, ICU, reuse of previous messages, positions, and freezing, and is not a CPU profiler value.
- `candidateOtherMs`: the remainder after subtracting the three intervals above from each sample's `readAndCandidateMs`. It may include the candidate map, filtering, base stat, and clock wrapper overhead. It is computed per raw sample before summarizing, and per-interval p95s are not subtracted from or added to each other.

All four values are inside `readAndCandidateMs`. Because of clock and extra Promise wrapper costs, it does not claim a performance change or optimization effect compared with a run without this instrumentation. This option does not change the browser prebundle settings. Deletion, error paths, and multi-file edits are outside this single-file normal-edit measurement.

```sh
node benchmarks/live-update/run.mjs --server-file-stages --out benchmarks/results/live-update-server-files.json
```

The measurement results are in [../results/live-update-server-files.json](../results/live-update-server-files.json). The run options are also recorded in `instrumentation`. The conditions are warmup 5, 50 measurements, and 25 controls, with detailed CPU and browser instrumentation off.
## Browser stage instrumentation

`--browser-stages` uses a Vite transform in `browser-profile.mjs` to wrap `applyCatalogPatch`, `freezeCatalogs`, `createLoadedSnapshot`, and `createBoundTranslator` in the client module, along with the signature construction. Library source and dist are not modified. `browser-probe.mjs` sums the synchronous time of each function from just before the edit through the DOM commit and records the call counts. Every interval must be observed for each sample, and the 4 transformed modules are confirmed. Startup, initial boot, and control round trips are excluded from the interval summary.

The snapshot time includes the translator and signature. Do not add nested values or per-interval p95s together. receive→commit also includes asynchronous coordination and the React commit outside the functions. This instrumentation is not a browser CPU profiler and includes clock call costs.

So that the transform does not hide inside the Vite dependency prebundle, this option disables prebundling of Saylo core, the React adapter, and the Vite client. React and ReactDOM remain prebundled. Therefore do not compare directly with a run without the option; compare **before and after under the same option**. Check the end-to-end change under normal development settings separately with a run that omits the option.

```sh
node benchmarks/live-update/run.mjs --browser-stages --out benchmarks/results/live-update-browser-before.json
```

The baseline measurement is in [../results/live-update-browser-before.json](../results/live-update-browser-before.json), and the measurement under the same option after reusing the immutable signature is in [../results/live-update-browser-after.json](../results/live-update-browser-after.json). The post-optimization result under normal settings with prebundling is [../results/live-update-signature.json](../results/live-update-signature.json), produced with `node benchmarks/live-update/run.mjs --out benchmarks/results/live-update-signature.json`. Each run used warmup 5, 50 measurements, and 25 controls, with the CPU profiler off. Load differed at run time, so do not attribute the entire end-to-end decrease to the signature change.

## CPU profile

With `--cpu-profile`, a `node:inspector` Session profiles only the edit loop during measurement and puts `cpuProfile` in the result. Startup, calibration, and warmup are excluded; fixture preparation, HTTP, and waiting are included, and this is not browser CPU. `topSelf` is self time, and `sayloInclusive` is inclusive time for frames from `packages/core|vite|typegen/dist`.

The summary mixes profiler control overhead (`node:inspector:post`) and OS scheduling delays, and absolute values differ between runs even for the same code. Do not compare profiler numbers between runs directly. `inclusiveMs` overlaps across nested frames, so do not sum it as a total.

## Parser cost comparison

Measure parser internal intervals with `node benchmarks/live-update/parser-stages.mjs`. The optional first argument is the output path, and the default is `benchmarks/results/parser-stages-before.json`. The default `incremental` mode uses a Node hook to wrap JSON processing, strict parsing, token scanning, position indexing, the message loop, and final freezing. It does not modify source or dist and confirms 2 transformed modules. It runs warmup 10 and 50 measurements, and does not attach a clock to each message. Detailed definitions and past baseline results are in [../../docs/11-parser-measurements.md](../../docs/11-parser-measurements.md).

The second optional argument, `cold`, runs warmup 5 and 20 measurements without a previous catalog. It confirms 3 transformed modules (catalog, json, and schema) and records AST construction, argument inference, argument schema freezing, and message freezing separately. GC is correlated with the parse interval using `PerformanceObserver` occurrence times, and overlapping GC time is counted as a union. It does not force GC, treat the heapUsed difference as total allocation, or subtract GC time from parse time. Both modes write `saylo-parser-stages-v2` results with raw samples separated into the file named by `samplesFile`. Results that include the overlapping JSON, message loop, and argument inference metrics and instrumentation overhead follow [../../docs/17-cold-parser-measurements.md](../../docs/17-cold-parser-measurements.md).

```sh
node benchmarks/live-update/parser-stages.mjs benchmarks/results/parser-stages-cold-final.json cold
```

The key-decoding trial files `parser-stages-key-after.json`, `parse-compare-key.json`, and `live-update-key.json` are results from experimental code that was reverted. The final position indexing optimization is kept separate in `parser-stages-position-after.json` and `live-update-position.json`. Do not mix normal screen update numbers with parser-only numbers.

`parse-compare.mjs` alternates calls to the baseline parser and the current parser in one process to compare only the parser's own cost. It extracts the baseline `packages/core/src` from git into a temporary directory and compiles it with `tsc`, so the current `packages/core/dist` build must exist. It edits one value to the same length, then calls both parsers alternately and excludes `JSON.stringify`, the equality check, disk, the watcher, validation, and the browser from measurement. It deletes the temporary directory when finished.

```sh
node benchmarks/live-update/parse-compare.mjs 4d1f6fc benchmarks/results/parse-compare.json
```

The first argument is the baseline revision and the second is the result path. After warmup, the result contains `beforeMs`, `afterMs`, and `afterMinusBeforeMs` per pair, `before` and `after` summaries, `pairedDifference`, and `currentCodeHashes`.

The optional third argument, `cold`, compares parses that run every time without a previous catalog. The current parser shares the same argument schema within one call but builds the AST and message positions separately. It keeps warmup 50 and 100 pairs for the default `incremental` mode, and cold runs warmup 5 and 20 pairs. Source preparation and the equality check are excluded from timing, and the entire parsed catalog is compared for each pair. The simple-message optimization was checked with `node benchmarks/live-update/parse-compare.mjs a7367b9 benchmarks/results/parse-compare-simple-cold.json cold`. The locale-add remeasurement under the same settings and the result with no p95 improvement are also recorded in [../../docs/15-simple-message-parser.md](../../docs/15-simple-message-parser.md).

Argument schema sharing was compared with `node benchmarks/live-update/parse-compare.mjs 4b69398 benchmarks/results/parse-compare-schema-sharing-cold.json cold`. Run the internal instrumentation with `node benchmarks/live-update/parser-stages.mjs benchmarks/results/parser-stages-schema-sharing-cold.json cold`; this fixture records 2 argument freezing calls, one for the empty contract and one for the name contract. It improved in 17 of 20 pairs and in the median, but p95 increased. Run conditions, raw results, and the remaining message freezing cost follow [../../docs/18-shared-argument-schemas.md](../../docs/18-shared-argument-schemas.md).

## Actual before-and-after comparison of the message map optimization
`locale-compare.mjs` supports `--experiment owned-map` in addition to the existing `ast-seal` scope. This scope permits only changes to the two core sources `catalog.ts` and `diagnostics.ts` plus the related catalog tests. It rejects changes that mix in other product sources, public entries, or package changes. Select `--mode edit` or the default `locale-add`, and use `--server-file-stages` to enable file interval instrumentation for both variants.

```sh
node benchmarks/live-update/locale-compare.mjs --experiment owned-map --mode edit --baseline 49fe1eb --current 8046a31 --server-file-stages --out benchmarks/results/owned-map-edit-comparison.json
node benchmarks/live-update/locale-compare.mjs --experiment owned-map --mode locale-add --baseline 49fe1eb --current 8046a31 --server-file-stages --out benchmarks/results/owned-map-locale-comparison.json
```

Defaults are 25 measured, 5 warmups, and 10 controls per run, in the order before/after/after/before. Each run uses fresh fixtures, the Vite optimizer, and a browser, shares external dependencies, and links workspace aliases to variant-specific copies. It restores the two selected sources from the Git refs and builds core with the same TypeScript. The original checkout dist is not modified, and on exit it verifies hashes and cleans up the temporary directory. The result's `snapshotSourceRevision` is the product source ref, and `gitRevision` is the common harness checkout. The comparison runner and policy hashes are also recorded.

`--smoke` runs only small once before and once after and deletes the results after keeping them temporarily. Do not use it for performance judgments. The policy check is `node --test benchmarks/live-update/comparison-policy.test.mjs`. Pooled quantiles combine the raw samples from both runs and are not an average of per-run p95 values. A fixed-order run on a single machine does not establish per-sample pairing, random assignment, or causality.

## Parser-only CPU profile

Build core first, then run the two commands below in sequence. They target a single file with 10k messages and do not start a browser or Vite. The last argument is the number of measured calls (default 100, range 1 to 1000).

```sh
node benchmarks/live-update/parser-cpu.mjs incremental benchmarks/results/parser-cpu-incremental.json 100
node benchmarks/live-update/parser-cpu.mjs cold benchmarks/results/parser-cpu-cold.json 100
```

Text and input JSON are prepared before profiling, and incremental warmup 50 and cold warmup 5 are excluded. `parser-cpu.mjs` requests an inspector sampling interval of 1000 µs and stores the actual original `.cpuprofile`, per-function summaries, line ticks at dist locations, call wall times, and code hashes. There is no detailed parser clock conversion or forced GC. Negative timeDelta values are kept in the original as they are, and shares are computed from sample counts instead of time weights.

Attributable samples from `parserStack` plus `coreWithoutParserStack` form the denominator for per-function shares. GC, idle/program, and unassignable samples are separate. When a caller is omitted from a core stack, the sample is not discarded and missing parents are not joined arbitrarily. Samples from the anonymous runner may hide actual parser cost, so they are not confirmed as runner overhead. V8 inlining, native attribution, and JIT state can affect the function and line distribution. Inclusive shares overlap and are not exact CPU time or allocation. All JSON strings are retained in advance, so the heap state also differs from a real watcher.

The summary check is `node --test benchmarks/live-update/parser-cpu-summary.test.mjs`. The current collection results and next candidates are in [48-parser-cpu-profile.md](../../docs/48-parser-cpu-profile.md). Do not claim a performance improvement or achievement of the screen update target from wall-time p95 with the profiler enabled.

## Limits

- The numbers are headless Chromium/Edge development-mode values from a single local run in a warm state. They are not a general guarantee and vary with hardware and load.
- In most recorded runs, the save→DOM ack p95 for both scenarios exceeded the target p95 of ≤ 100 ms. Before optimization, small (1k×3) p95 was 191.25 ms and large (10k×20) p95 was 1693.98 ms; after optimization they were 131.27 ms and 819.55 ms, and both exceeded the target. The first run after applying request-scoped patches was 224.31 ms for small and 229.43 ms for large, and the rerun was 76.65 ms for small and 241.18 ms for large. The parser run with the profiler off was 69.82 ms for small and 200.63 ms for large. Although some runs brought small within the target, values differ between runs of the same code, so no stable achievement is claimed. In every large-scenario run listed up to that point, p95 exceeded the 100 ms target. A later JSON leaf edit run had large p95 of 95.25 ms (24 of 25 within 100 ms) and met the target, while the locale-add large run had p95 of 268.58 ms (23 of 25 within 250 ms) and failed to meet the 250 ms target; see [../../docs/59-json-leaf-edits.md](../../docs/59-json-leaf-edits.md) for details.
- Before-and-after values come from separate single runs with the same fixtures and options (warmup 5, 50 samples, 25 controls). The control round-trip p95 also decreased, from 10.51 to 6.21 ms for small and from 39.69 to 11.53 ms for large, so the entire decrease cannot be attributed to the code change, and it is not a general guarantee.
- In the first request-scoped patch run, fileWrite p95 (61.51 ms versus 8.92 ms) and server broadcast p95 (199.82 ms versus 64.99 ms) were larger than in the rerun. There is no independent load profile, so the cause is not determined.
- Runs with the CPU profiler enabled mix in overhead and OS scheduling delays and may include large delays. The save→DOM ack p95 of 1074.94 ms in [../results/live-update-profile-after.json](../results/live-update-profile-after.json) differs from [../results/live-update-parser.json](../results/live-update-parser.json) (large p95 200.63 ms) for the same code with the profiler off, and the cause of the large delay is not determined.
- The `readAndCandidateMs` in `serverStages` is a combined read and parse value. The two costs are not split and confirmed separately.
- `parse-compare.json` compares only parser cost for editing one file with 10,000 messages. It is not extended to end-to-end latency or a claim of p95 improvement.
- Startup timing measures the Vite server boot and browser boot separately. Paint timing is not instrumented.
- Locale add and delete latency, paint, virtualization comparisons, comparisons with other libraries, and bundle size measurement are outside this scope.
