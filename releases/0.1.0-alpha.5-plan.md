# 0.1.0-alpha.5 릴리스 계획

이 문서는 게시 전 계획이자 후보 실행 결과 기록이다. 최신 검증 후보의 제품 소스는 `109afe749a2bf7728394b70796eef396e9891aab`(`109afe7`)이며 후보는 `.release/candidate-0.1.0-alpha.5-DhQ1s3`, 검증은 `validation-pAOEjE`다. 공개 다섯 `packages/*/package.json`은 아직 `0.1.0-alpha.4`다. 소스 버전 승격, 푸시, workflow dispatch, npm 게시는 하지 않았다.

2026-10-23 새 후보 `109afe7`은 현재 번역 작업 흐름(`export`·`import`·`refresh`·`approve`, context·format·diff)을 포함한다. 이 후보는 검증 후보이며 게시본이 아니다. `4765870`의 검증 기록은 아래 역사 기록으로 보존한다.

2026-10-22 소스 개선 `9abe013`·`cf90bfc`·`8dfd11f`·`ebc100c`는 `4765870` 후보에 포함되지 않는다. 갱신 전송 예외 격리, 시간·I/O·Worker 주입, 호출별 취소와 인스턴스 수명 취소, revision 상한 검사, 임시 파일 소유권과 오래된 Worker 완료 격리를 추가했다. 검증 기록은 [실행 경계 개선](../review/runtime-boundaries-2026-10-22.json)에 있다.

2026-10-13에 사용자가 기능 개발을 다시 시작했고 게시는 보류로 둔다. 그날의 동결 후보 `.release/candidate-0.1.0-alpha.5-Zs8WKy`(소스 `500238f`)는 자기 입력에 대한 역사 기록으로 남고, 새 rich text core API(`tParts`) 코드는 포함하지 않는다. 2026-10-21(KST)에는 자동분석 보완을 반영한 소스 `4765870`에서 후보 `.release/candidate-0.1.0-alpha.5-OTQgQh`를 검증했다. source freeze 이후 이 문서는 각 후보의 실행 결과를 기록한다.

공개 게시 범위는 `@0disoft/saylo-core`·`@0disoft/saylo-react`·`@0disoft/saylo-svelte`·`@0disoft/saylo-typegen`·`@0disoft/saylo-vite` 다섯 패키지다. `packages/vue`는 게시하지 않는 Vue workspace(`private: true`)라 게시 다섯 패키지에 넣지 않고, 이번 승격에서도 `version`은 `0.1.0-alpha.4`, `private: true`를 그대로 둔다. 이 workspace가 `@0disoft/saylo-core`를 exact로 참조하므로 공개 core 버전이 올라가면 그 내부 참조와 루트 `package-lock.json`의 `packages/vue` 항목도 새 버전에 맞춘다.

이 후보 소스에는 새 catalog CLI, import diff, typegen의 SvelteKit nested build 수정이 들어간다. 관리 콘솔 `4d79fe7`의 local tarball 및 registry alpha.4 tests는 [82-admin-support-pilot.md](../docs/82-admin-support-pilot.md)에 별도 pilot 근거로 기록했다. 이 후보 자체의 SvelteKit browser·registry 검증은 하지 않았으며 이전 후보의 supplemental 결과를 재사용했다고 주장하지 않는다. Vue workspace는 `private: true`, 원본 여섯 workspace 패키지 버전은 alpha.4로 유지했고 push·version bump·publish·workflow dispatch는 하지 않았다.

## alpha.4 이후 추가

아래는 게시된 alpha.4에 없고 alpha.5 후보에 들어가는 변경이다.

- Rich text: `@0disoft/saylo-core`에 `tParts` 기반 rich text API가 들어간다. 아직 게시본 `0.1.0-alpha.4`에는 없다.
- 자동 선택 빌드: `includeKeys`가 `{ from, dynamicKeys? }` 입력으로 자동 키 분석을 지원한다. `4765870` 후보의 설치된 automatic key analysis/build, no-alias, 추가 catalog 조회 0은 `pack.log`에서 확인했다. exported/default/return 번역함수 참조가 분석 밖으로 전달되는 경로의 동적 키 처리도 보완했다. 해결되지 않은 동적 키에는 `dynamicKeys`를 요구한다.
- 구독 catalog push: 실제 Vite watcher/WebSocket push 경로를 포함한다. 후보 검증에서 push가 PASS였다. Rich text·선택 빌드·push 관련 근거는 문서 `docs/78`·`docs/08`, `packages/vite/README.md`다.

- 개발 연결 상태: `connectDev`의 `onSyncState` 옵션 콜백이 eager·lazy 두 경로에서 handshake 상태 `{ status, attempt, maxAttempts: 3 }`(frozen)를 넘긴다. 상태 타입 `DevSyncState`는 `@0disoft/saylo-vite/client`에서 export하는 타입이다. lazy는 `DevCatalogSource`의 선택 메서드 `getSyncState`·`subscribeSyncState`로 접근해 기존 외부 source와 타입 호환이 유지된다. 구현 `b534b4f`, 계약 [개발 동기화 상태](../docs/dev-sync-state.md), 수락 [상태 관측](../review/dev-sync-state-acceptance-2026-10-11.json)·[예제 UI](../review/dev-sync-ui-acceptance-2026-10-11.json).
- 문의용 진단 API: `@0disoft/saylo-vite/client`가 함수 `createSupportReport`·`createSupportRecorder`를 export한다. 허용 목록 투영 위에 세워 오류 문구·파일 이름·로케일·키·인자·요청 ID·경로·스택을 버퍼에 원문으로 담지 않고, 자동 수집·전송 경로가 없다. 스키마는 `saylo.support/v1`이다. 구현 `d7097dc`, 계약 [문의용 진단 보고서](../docs/support-report.md), 수락 [API](../review/support-report-api-2026-10-11.json)·[예제 UI](../review/support-report-ui-2026-10-11.json).
- lazy observer 실패 격리: lazy update observer가 던진 예외가 handshake·타이머 정리·다른 observer를 막지 않고 `onDiagnostic`으로 보고된다. `LiveDiagnostic.operation`이 `handshake`와 `observer`를 구분한다. 구현 `c8297c8`, [회귀](../review/lazy-update-observer-2026-10-11.json).
- 시작 안내와 문의 창구: `docs/getting-started*.md` 네 편과 문의 이메일(rodisoft1@gmail.com)을 `SUPPORT.md`·`SECURITY.md`와 다섯 패키지 metadata(`bugs.email`·`homepage`)에 반영했다. 구현 `ccff67a`, 수락 [시작 안내](../review/getting-started-acceptance-2026-10-11.json)·[공개 창구](../review/public-reporting-destination-acceptance-2026-10-11.json).

- 선택 빌드(includeKeys): Vite 플러그인 `saylo()`에 배열 `includeKeys`를 넘기면 build에서 내보낼 메시지를 `namespace:messageId` 정확 목록으로 고른다. 배열 입력은 와일드카드 없이 정확 목록을 손으로 관리하는 방식이다. 형식 오류·목록 내 중복은 플러그인 생성 시점에, 기준 카탈로그에 없는 키는 build 시점에 던진다. 옵션을 생략하면 원본 전체를, `[]`를 주면 로케일·namespace 위상은 그대로 두고 메시지가 0개인 카탈로그를 내보낸다. 개발 서버와 typegen은 원본 전체를 보고, eager·lazy·SSR은 같은 투영을 쓴다. `__proto__` 같은 키도 일반 메시지로 직렬화한다(투영 레코드는 `Object.create(null)`, emit하는 JS는 `__proto__`가 있으면 `JSON.parse`). 구현 `bb3a3fa`, 아직 게시되지 않은 기능이며 게시본 `0.1.0-alpha.4`에는 없다.
- 선택 빌드 예제: vanilla 스타터에 `--mode selected` 비교 build와 `verify:demo:selected`를 붙였고, React 스타터는 typegen이 만든 타입 키와 `includeKeys` 목록을 맞춘다(`verify:demo:react:selected`). 구현 `0a2b34f`(vanilla), `a605325`(React).
- 게시하지 않는 Vue workspace(`private: true`): `packages/vue`는 게시 다섯 패키지에 넣지 않으며 버전은 `0.1.0-alpha.4`로 유지한다. 전체 검사에는 Vue 어댑터 검사가 포함되지만, 게시 대상 tarball은 다섯 패키지로 유지하고 Vue tarball은 넣지 않는다. 상세 범위는 위 "후보 기준"을 따른다.

## alpha.4에 이미 있던 것

아래 기능은 alpha.4 게시본(`d26506f`)에 이미 들어 있어 이번 릴리스의 신규 변경으로 세지 않는다. React `useI18nSelector`와 Svelte `selectSvelteStore`·`getI18nSelector`, compact 카탈로그 전송, `astRuntime`, `requireCompleteTranslations`, typegen 경쟁 상태 수정과 Vite 디스크 재확인, owned message map freeze, JSON leaf 편집, 검증 결과 재사용이다. 상세는 [alpha.4 릴리스 기록](0.1.0-alpha.4.md)에 있다.

alpha.4 소비 검증 명령(`verify:registry:alpha4`, `verify:registry:sveltekit:alpha4`)과 과거 버전 명령은 그대로 둔다.

## 게시 전에 할 일

### 1) 버전 4 소스에서 alpha.5 후보를 동결·검증

- 후보 도구는 커밋된 HEAD를 복사해 그 사본의 공개 다섯 패키지 버전·내부 의존과 게시하지 않는 Vue workspace(`private: true`)의 `@0disoft/saylo-core` 참조를 새 버전으로 올린다. Vue의 `version`·`private: true`는 그대로 둔다. 원본이 이미 alpha.5면 `release:candidate --version 0.1.0-alpha.5`가 "A proposed candidate must use a new version."으로 실패한다. 후보는 원본이 alpha.4인 지금 상태에서 만든다.
- 추적된 미커밋 변경이 있으면 동결이 거부된다. 후보 범위 커밋을 먼저 정리한 뒤 `npm run release:candidate -- --version 0.1.0-alpha.5`와 `npm run release:candidate:verify -- --candidate .release/candidate-0.1.0-alpha.5-<suffix>`를 실행한다.
- 검증은 원본 커밋의 입력 전체를 Git 객체와 대조하고, 사본에서 `npm ci`, `check`, `release:check`, 독립 JS/TS tarball 소비, 게시 계획 dry run을 돌린 뒤 새 `validation-<suffix>/`에 tarball·로그·manifest를 남긴다.
- 이 기록이 위 후보 근거다. 여기서 나온 tgz는 로컬 proof이고 게시 대상이 아니다.

### 2) 승인 후 원본을 alpha.5로 승격

- 다섯 `packages/*/package.json`의 `version`과 내부 의존 `@0disoft/saylo-*`를 exact `0.1.0-alpha.5`로 올린다.
- `packages/vue/package.json`은 `version`을 `0.1.0-alpha.4`, `private: true`로 그대로 두고 `@0disoft/saylo-core` 내부 의존만 exact `0.1.0-alpha.5`로 맞춘다. 루트 `package-lock.json`의 `packages/vue` 항목도 버전은 alpha.4로 두고 core 의존만 alpha.5로 맞춰 루트 `npm ci`가 워크스페이스와 어긋나지 않게 한다.
- 게시하지 않는 Vue workspace(`private: true`)가 있는 지금은 이전 후보의 여덟 파일 승격 패치를 그대로 쓸 수 없다. 그 패치는 공개 다섯 `package.json`·루트 lock·SvelteKit lock·`release.yml`만 다뤘고 `packages/vue`와 루트 lock의 `packages/vue` 항목이 없다. 승격 시에는 이 두 곳이 더해지고, Vue의 `version`·`private`는 그대로 두며 게시 다섯 패키지 수는 늘리지 않는다. 그 패치가 현시점에서도 적용되는지는 새로 검증하지 않았으므로 "적용 가능"으로 주장하지 않고, 승격 커밋에서 새 patch를 만들어 로컬 검증으로 확인한다.
- 같은 exact 문자열로 루트 `package-lock.json`의 다섯 workspace 항목과 내부 의존 범위, `examples/sveltekit/package-lock.json`의 `node_modules/@0disoft/saylo-*` 네 leaf 항목과 내부 의존 metadata를 맞춘다(`file:` 링크 경로는 그대로 둔다).
- `.github/workflows/release.yml`의 `version` 입력 기본값을 `0.1.0-alpha.5`로 바꾼다.
- 후보 표시와 게시 상태를 구분하도록 남은 문구를 이 승격 커밋에 모아 정리한다. 대상은 `README.md`, `SUPPORT.md`, `SECURITY.md`, `docs/README.md`, `docs/dev-sync-state.md`, `docs/support-report.md`, `docs/09-release.md`, 다섯 `packages/*/README.md`이고, 동봉 묶음은 `npm run build:docs`로 다시 만든다.
- `release:check`는 다섯 manifest의 버전·라이선스·engines·publishConfig·내부 의존, 루트 `private`, `LICENSE`·`NOTICE` 일치를 검사하며 두 lock은 읽지 않는다. lock 동기화는 설치와 소비 검사가 맞는지로 확인한다.
- 승격 커밋에서 로컬 `npm run check` → `npm run release:pack` → `npm run release:publish -- --version 0.1.0-alpha.5 --tag alpha`를 돌린다. 이 pack도 proof이고 게시 바이트는 아래 CI가 만든다.
- 후보를 동결한 뒤 문서를 더 고치면 위 후보 기록은 그 시점 커밋 기준으로만 유효하다. 승격 뒤에는 원본 버전이 alpha.5라 후보 동결 명령을 다시 돌릴 수 없으므로, 문서·버전을 고칠 때는 승격 커밋을 고치고 로컬 검증을 다시 돌린다.

### 3) 묶음 push와 단일 릴리스 workflow

- 승격 커밋을 묶어 `main`에 한 번에 push한다. 검증 횟수와 러너 사용을 줄이려고 push와 게시를 한 단위로 묶는다.
- `release.yml`을 `version=0.1.0-alpha.5`, `dist_tag=alpha`, `publish=true`, `verify_oidc=true`로 한 번 dispatch한다. 단일 job이 `release:check` → `npm ci` → `audit:dependencies` → `check` → `release:pack` → `release:publish`(dry run) → artifact 업로드 → OIDC 게시 순서로 돈다.
- 게시되는 tarball은 CI가 커밋된 alpha.5 소스에서 직접 pack한 것이고, workflow가 남기는 `saylo-npm-0.1.0-alpha.5` artifact가 그 산출물이다. 로컬 후보·로컬 pack tgz는 게시 대상이 아니다.
- CI artifact의 manifest를 `releases/0.1.0-alpha.5.json`으로 옮기고 `releases/0.1.0-alpha.5.md`를 쓴다. 이 두 파일은 아직 없다. 만든 뒤 이 문서의 참조를 링크로 바꾼다.
- 게시는 원자적이지 않다. 중간에 실패하면 이미 올라간 패키지만 남으므로 다시 dispatch하며, tarball integrity와 요청 dist-tag가 둘 다 같은 패키지만 건너뛴다. integrity가 다르면 같은 버전을 지우지 말고 새 릴리스 버전을 정한다.

### 4) registry integrity 대조와 소비 인수

- 준비된 `verify:registry:alpha5`(`pack-smoke.mjs --registry --registry-version 0.1.0-alpha.5`)와 `verify:registry:sveltekit:alpha5`(`pack-sveltekit.mjs --registry-version 0.1.0-alpha.5`)를 CI 승인 manifest를 확보한 뒤 실행한다.
- 앞 명령은 `releases/0.1.0-alpha.5.json`의 승인 SHA-512와 registry metadata·다운로드한 tarball을 대조하고, 저장소 밖 JS/checkJs·TS 앱에 설치해 CLI·typegen·README 예제·public subpath·React/Svelte SSR·Vite production lazy를 확인한다.
- 뒤 명령은 같은 승인 tarball로 독립 SvelteKit 앱을 설치해 svelte-check 0 errors·0 warnings, client/SSR 빌드, 동시 ko/en SSR과 boot 일치, listener 정리·idempotent stop·late connection 취소, Node 운영 HTTP, Chromium hydration·ko/en/ko 전환·공통 layout 상태를 확인한다.
- alpha.5 이후의 registry 검사는 동봉 문서·CLI 도움말·문의 진단 API·동기화 상태 콜백과 정리를 필수로 확인한다. API가 빠지면 검사를 건너뛰지 않고 실패한다. SvelteKit은 고정한 `scripts/pack-fixtures/sveltekit-registry-alpha5`로 상태 관측과 보고서 생성·초기화를 검사하며, 기존 alpha.1~4는 기존 검사 경로를 유지한다. 로컬 tarball로 새 예제를 검사하는 `npm exec -- node scripts/pack-sveltekit.mjs --consumer-fixture support`는 준비 검증이며 registry 인수 결과가 아니다([근거](../review/registry-consumer-contract-acceptance-2026-10-12.json)).
- `verify_oidc=true`·`publish=false` dispatch로 다섯 Trusted Publisher 인증을 게시와 별개로 확인할 수 있다. 게시 후 조회가 곧바로 새 버전을 못 보여 줄 수 있으므로 재게시 없이 조회·다운로드가 가능해질 때까지 기다린 뒤 인수 검사를 돌린다.

### 5) 후보를 시험한 소비 앱을 되돌리기

- alpha.5 후보를 시험한 앱은 직전 정상 커밋의 앱 코드·`package.json`·lock으로 되돌린다. 후보에서만 쓰던 새 API 호출과 후보 버전 참조가 함께 사라진다.
- 되돌린 lock으로 의존성을 다시 설치해 실제 트리를 맞춘다. registry에서 받는 버전은 게시본 alpha.4다.
- 후보를 쓰지 않은 앱은 그대로 두면 된다. `@alpha` tag가 alpha.4를 가리킨다.
- 저장소(라이브러리) 소스의 버전을 alpha.4로 되돌리는 작업은 이 계획에 없다.

## 주장하지 않는 것

- 새 성능 수치를 내지 않는다. [alpha.4 기록](0.1.0-alpha.4.md)의 warmed 로컬 p95 값은 그대로이고 이번 후보로 다시 측정하지 않았다.
- 게시, registry 인수, CI 승인 artifact를 아직 만들지 않았다. 후보 검증은 로컬 결과다.
- 접근성은 axe-core 4.14.0 검사와 Chromium의 키보드·페이지 확대 검증 범위다. 다섯 예제의 ko/en에서 100/400% 키보드 핵심 작업 20흐름과 100/200/400% 페이지 확대 60상태를 확인했다([키보드 흐름](../review/demo-keyboard-journey-acceptance-2026-10-12.json)·[페이지 확대](../review/demo-page-zoom-acceptance-2026-10-12.json)). 대비 incomplete는 기록에 유지한다. 실제 화면 읽기 음성·OS 글자 확대·다른 브라우저는 미검증이다. 내레이터 자동 검증은 Windows 권한 경계에서 중단했고, 사용자가 종료한 뒤 실행했던 PID의 부재만 확인했다([중단·정리 기록](../review/screen-reader-verification-blocker-2026-10-12.json)).
- Renovate는 로컬 config 검증만 했고 봇 활성화·대시보드 승인을 하지 않았다([정책 수락](../review/dependency-policy-acceptance-2026-10-12.json)).
- registry의 다섯 `alpha` tag는 `2026-10-12` 이전 이력에서 alpha.4를 가리켰다([registry 관측](../review/release-alpha5-registry-preflight-2026-10-12.json), 관측 시각 `2026-10-11T16:11Z`). 지금은 원격 tag를 다시 조회하지 않았으므로 새 실물 관측으로 주장하지 않는다.
